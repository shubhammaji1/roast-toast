### Mobile performance

Lighthouse 12.8.2 used simulated mobile throttling and a 390 × 844 viewport against a local production build backed by an isolated, seeded database. The homepage values below are medians of three cold runs. The other pages have one cold run each. The audit targets are Largest Contentful Paint (LCP) ≤ 2.5 seconds and a performance score of at least 90.

| Page | Performance | LCP | Accessibility |
|---|---:|---:|---:|
| Homepage | 69 | 4.00 s | 100 |
| Explore | 57 | 4.48 s | 100 |
| New idea | 43 | 5.23 s | 100 |
| Saved | 59 | 3.91 s | 100 |

The local pre-change homepage median was 73 and 3.65 s. After the changes, median homepage JavaScript transfer fell from 244 KB to 183 KB and initial idea-list requests fell from six to three. The reduced payload did not translate to a better Lighthouse score or median LCP in these runs. The final homepage performance scores ranged from 45 to 69, with a blocking-time outlier on the first run. The earlier hosted audit used a different environment and dataset. See the [final Lighthouse data](../.data/qa-fixes/performance.json) and [local baseline data](../.data/qa-fixes/performance-first-attempt.json).

## Implementation tradeoffs

The installed Next.js version exposes CSS inlining through `experimental.inlineCss`. It removes a blocking stylesheet request on a full navigation. The roughly 16 KB compressed stylesheet then travels with the HTML on full navigations, which increases document size. This behavior applies to production builds.

The supplied font faces retain the design's family/weight choices. Assets carry content digests and their licenses. See `apps/web/public/fonts/README.md` when updating them. Normal system fallback covers glyphs outside the supplied Latin subset.

Automatic navigation prefetch is disabled for shell navigation and idea cards to reduce unsolicited downloads. Clicking links still uses Next.js client navigation.
